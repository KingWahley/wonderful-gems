Anatomy of a Collapse: Why did 99.79% of requests fail?

The k6 load test results revealed a dramatic collapse: out of 71,627 total requests, only the initial 148 requests completed successfully. All subsequent requests dropped instantly, returning an exact latency of 0.00ms.

In network operations, a 0.00ms response time is a signature symptom of a Connection Refused (connectex) event. The server didn't just slow down; it went completely offline. Here is the exact technical breakdown of why this occurred:

  • Supabase PostgreSQL direct limit reached (60 Socket Cap): The application connected directly to the PostgreSQL database. The Supabase free-tier database enforces a strict ceiling of 60 concurrent direct connections. As 500 Virtual Users loaded dynamic marketing pages, each page initiated database requests to fetch blog posts, destinations, and tours. This instantly exhausted the 60-socket ceiling. Excess requests threw unhandled database connection exceptions that crashed the Node.js process.
  • Dev-Mode JIT Compiler memory stack collapse (OOM): Running in local development mode (npm run dev) involves heavy Just-In-Time (JIT) compilation and hot-reloading overhead. Processing 500 VUs navigating dynamic files simultaneously exhausted the maximum memory heap of the single-threaded Node JIT compiler, triggering an Out-Of-Memory (OOM) process termination.
Edge Caching Safeguard

Our Solution: Global 60-Second Edge Caching Shield

To prevent these failures and scale the architecture to withstand thousands of concurrent VUs, we replaced all dynamic rendering flags with a global 60-second revalidation mechanism (Incremental Static Regeneration - ISR) across all public marketing pages.

This single change creates an iron-clad protection shield around the application and database:

  • 99% database workload reduction: Instead of connecting to Supabase on every single page load, Vercel Edge networks compile and store the page statically. For 60 seconds, millions of concurrent hits are served directly from memory, resulting in exactly **one** database request per minute per route.
  • 15ms ultra-low latency: Serving pages from the global Vercel Edge CDN bypasses server computing, React rendering, and database queries. This slashes average page loads from several seconds to a blazing **15ms**.
  • Protection against Virality & DDOS: With caching active, rapid spikes in traffic (like our 500-VU stress test) never reach the database or the core servers. The CDN deflects 100% of the read load, preventing server crashes or rate limits.
